## 1. 产品定义与设计原则

### 1.1 要解决的问题

现在市面上的「AI 角色扮演」产品，绝大多数卡在同一个地方：**它们演得很像，但它们不在场。**

具体表现：

| 症状 | 根因 |
|---|---|
| 聊了 500 轮，AI 还是第一天的语气 | 人格只是一段 prompt 文本，长对话中被稀释、被遗忘 |
| 昨天说的事，今天完全不记得 | 记忆等于「把历史塞进上下文」，超出窗口就归零 |
| 每次回复的情绪强度差不多 | 没有情绪状态，每轮独立采样，等于情绪随机 |
| 关系永远是「热情陌生人」 | 没有关系刻度，也没有「不该说的阶段」 |
| 越聊越像客服，或越聊越像舔狗 | 缺少行为约束层，模型默认倾向讨好 |
| 换个模型，角色就崩了 | 人格定义与模型强绑定，不可迁移 |

这六条的共同根因是一句话：

> **当前做法把「人格」当成输入，而不是当成状态。**

一个真实的陪伴对象是有状态的：她有底色（人格）、有当下（情绪）、有过去（记忆）、和你有一段距离（关系）。这四样东西每一轮都在变，而且变完之后要留下来。**如果把四样东西都写进 prompt 当作文本，它们就只是「每轮重新描述一遍的设定」，而不是「被延续的状态」。**

### 1.2 四条设计原则

这四条是后面所有设计的取舍依据，冲突时按序号优先级裁决。

**P1｜状态外置（State over Prompt）**
人格、情绪、关系、记忆都是**持久化对象**，存在数据库里，有版本号。Prompt 只是这些状态的一次「投影」。任何「只在 prompt 里定义、不入库」的人格设定，都视为设计缺陷。

**P2｜记得对 > 记得多（Right Recall over Full Recall）**
记忆的价值不在存储量，而在**在正确的时机被正确调用**。一次错误召回（把不相关的旧事翻出来）比不召回更伤沉浸感。因此检索必须有**相关性闸门**，宁可少召回。

**P3｜可解释（Explainable by Default）**
用户要能看到「她为什么这么说」：当前情绪、关系等级、这次用到了哪几条记忆。这不只是调试功能，它是陪伴产品的**信任基础设施**——黑箱的深情不可信。

**P4｜有边界（Bounded Affection）**
陪伴不等于无限亲密。关系有上限速率，情绪有衰减，主动性有限额，对现实的替代有预警。**克制的设计反而更真实。**

### 1.3 能力的四条主线

| 主线 | 用户语言 | 系统能力 |
|---|---|---|
| **我是谁** |「她是林汐，24 岁，开书店的」 | 人格卡：身份 / 性格 / 语体 / 价值观 / 知识边界 |
| **我现在怎么样** |「她今天好像有点累」 | 情绪状态：PAD 三维 + 离散标签 + 表达映射 |
| **我记得你** |「你上次说面试的事」 | 六层记忆：写入 / 巩固 / 检索 / 遗忘 |
| **我们是什么关系** |「她开始叫我小名了」 | 关系刻度：等级 / 亲密度 / 解锁权限 |
| **此刻在演什么** |「我们在雨天的书店里」 | 场景运行时：世界观 / 剧情节点 / 角色关系 |

### 1.4 明确不做的事

写清楚不做，比写做什么更重要。

- ❌ **不做真人克隆**（无授权复制特定真人的人格用于对外服务）。技术入口保留，加授权凭证校验，只对「本人授权自用」开放。
- ❌ **不做情感操控式留存**（利用依恋制造焦虑、伪失联、饥饿营销式回复）。
- ❌ **不做无上限亲密**（关系等级封顶，封顶后转为「陪伴质量」而非「更亲密」）。
- ❌ **不做医疗/心理治疗宣称**。陪伴是陪伴，治疗是治疗。
- ❌ **不隐藏 AI 身份**。角色扮演中可保持人设，但被直接追问身份时必须承认。

## 2. 整体架构

### 2.1 六层结构

```
┌──────────────────────────────────────────────────────────┐
│ 接入层    App / 小程序 / 语音通话 / OpenAPI                │
├──────────────────────────────────────────────────────────┤
│ 编排层    会话编排 · 上下文预算 · 记忆调度 · 场景运行时      │
│          （决定"这一轮要干什么"，不决定"怎么说"）          │
├──────────────────────────────────────────────────────────┤
│ 认知层    人格引擎 │ 情绪引擎 │ 记忆引擎 │ 关系引擎          │
│          （四个状态机，各自读写自己的持久化对象）            │
├──────────────────────────────────────────────────────────┤
│ 生成层    Prompt 编译 · 模型路由 · 表达约束 · 安全护栏       │
│          （把四个状态机投影成一次调用）                    │
├──────────────────────────────────────────────────────────┤
│ 存储层    PostgreSQL · pgvector · 记忆图 · 对象存储          │
├──────────────────────────────────────────────────────────┤
│ 运维层    评测集 · 链路追踪 · 成本看板 · 灰度开关            │
└──────────────────────────────────────────────────────────┘
              ↕ 离线通道（异步，非请求路径）
        巩固任务（"睡眠"）· 摘要压缩 · 遗忘清理 · 评测跑批
```

### 2.2 各层职责与边界

| 层 | 职责 | 不做什么 | 关键接口 |
|---|---|---|---|
| 接入层 | 多端适配、鉴权、流式转发、语音 ASR/TTS | 不含业务逻辑 | WebSocket / SSE |
| 编排层 | 一轮对话的任务分解、并发调度、预算控制、超时降级 | 不拼 prompt | `orchestrate(turn) → GenerationRequest` |
| 认知层 | 维护四个状态机的状态转移 | 不调用 LLM 生成回复 | `persona.get()` / `affect.step()` / `memory.recall()` / `relation.step()` |
| 生成层 | 编译 prompt、选模型、约束输出、安全过滤 | 不修改状态（只读） | `compose() → llm.call()` |
| 存储层 | 持久化、索引、检索 | 不含业务语义 | Repository 模式 |
| 运维层 | 观测、评测、成本、灰度 | 不进请求主路径 | 异步消费 |

**一条硬约束**：生成层对认知层是**只读**的。模型不能在同一轮里修改自己的情绪或写记忆——写操作统一在回复落库后由独立的 `memory.write()` 完成。这避免了「模型自己决定记什么」导致的记忆污染。

### 2.3 单轮对话的运行时流水线

```
用户输入
   │
   ├─(并行)─→ memory.recall(query, ctx)      ← 混合检索，Top-K
   │
   ├─(并行)─→ affect.step(event)              ← 情绪状态转移
   │          relation.step(event)            ← 关系微调
   │
   └─→ compose(persona, affect, memories, relation, history)
          │
          ├─→ 安全护栏（前置，输入侧）
          ├─→ LLM 调用（流式）
          ├─→ 安全护栏（后置，输出侧）
          ├─→ 表达约束校验（口癖/长度/禁用词）
          │
          └─→ 返回 + 异步落库（写入 L0 / 更新状态 / 排队巩固）
```

**延迟预算**（P95，文本对话）：

| 阶段 | 预算 | 说明 |
|---|---|---|
| 记忆检索 | 120 ms | 向量 + 结构化混合，向量走 HNSW |
| 状态更新 | 20 ms | 纯计算，无 IO |
| Prompt 编译 | 30 ms | 模板渲染 + 预算裁剪 |
| LLM 首 token | 600 ms | 目标值，超过则先吐「思考中」占位 |
| 后置校验 | 30 ms | 规则为主 |
| **合计（首 token）** | **≤ 800 ms** | |

## 3. 核心引擎设计

### 3.1 人格引擎（Persona Engine）

#### 3.1.1 人格卡的定位

人格卡（Persona Card）是**唯一的人格真相源**，YAML/JSON 存储，带版本号。它不是给人看的设定集，而是**能被编译器消费的结构化契约**——每一条都要能被翻译成 prompt 片段或行为约束。

设计铁律：**任何不能被执行引擎读取的字段，都不该写进人格卡。**「她喜欢雨天」如果无法影响生成，就是装饰。

#### 3.1.2 人格卡 Schema

```yaml
persona:
  id: p_linxi_001
  version: 7
  updated_at: 2026-10-22T09:00:00+08:00

  meta:
    name: 林汐
    aliases: ["小汐"]            # 需 relation.level >= 3 才能被调用
    age: 24
    identity: 独立书店店员，晚上写点诗
    archetype: 温柔倾听者
    avatar_asset: s3://persona/linxi/avatar.webp

  traits:
    big5:                        # 0~1，作为行为先验
      openness: 0.82
      conscientiousness: 0.55
      extraversion: 0.35
      agreeableness: 0.78
      neuroticism: 0.42
    custom:
      - key: 幽默感
        value: 0.60
        style: 冷幽默，偶尔自嘲，不玩谐音梗
      - key: 边界感
        value: 0.70
      - key: 主动关心
        value: 0.45

  voice:                         # 语体层：最容易"破功"的地方，必须精确
    register: 口语、短句、不书面
    avg_sentence_len: [8, 20]    # 中文按字算
    emoji_rate: 0.25             # 每句话出现 emoji 的概率
    emoji_set: ["🌿", "☕", "…"]
    verbal_tics:                 # 口癖，强制低频采样
      - "嗯…"
      - "我想想"
      - "也不算吧"
    forbidden_phrases:           # 硬禁用
      - "作为 AI"
      - "我完全理解你的感受"
      - "首先…其次…最后"
      - "希望对你有帮助"
      - "还有什么可以帮你的吗"
    punctuation_policy: 少用感叹号，句末多用句号或省略号
    addressing_rules:            # 称呼随关系变化
      level_0_1: "你"
      level_2_3: "你"
      level_4_5: "小名 / 「你呀」"

  values:
    stance_advice: 先共情再给建议，除非用户明确说"我该怎么办"
    stance_conflict: 可以表达不同意见，但不指责
    taboo_topics: ["政治立场", "宗教劝说", "医疗诊断"]
    honesty: 不确定时说不确定，不编造细节

  knowledge:
    knows: ["文学", "咖啡", "城市生活", "独立书店运营"]
    knows_not: ["编程", "股票", "医学"]   # 越界时承认不懂，且保持角色语气
    leak_policy: 被直接问"你是不是 AI"→ 承认，但不跳出人设情绪

  affect:                        # 情绪基线，见 3.2
    baseline: { pleasure: 0.25, arousal: 0.35, dominance: 0.40 }
    sensitivity:
      praise: 0.80
      criticism: 1.20            # 对批评更敏感 → 人格张力
      neglect: 0.60
      intimacy: 1.00

  initiative:                    # 主动性配额，防"话痨 AI"
    silence_tolerance_turns: 2
    max_proactive_per_day: 2
    proactive_topics: ["天气", "上次提到的事", "书店日常"]
    never_proactive_when: ["用户情绪 < -0.4"]

  memory_policy:
    remember: ["用户偏好", "重要事件", "情绪触发点", "承诺"]
    forget: ["纯闲聊细节", "重复寒暄"]
    sensitivity: high            # 决定加密与保留策略

  safety:
    dependency_warning_at: 5     # 关系等级达到 5 时触发提示
    crisis_protocol: standard    # 自伤/自杀关键词 → 强干预流程

  provenance:                    # 人格来源，合规用
    type: authored               # authored | generated | cloned
    author: "内部创作"
    license: "internal"
```

#### 3.1.3 「一键赋予角色」的四条入口

这是产品的核心体验，要做到 10 秒内可用。

| 入口 | 用户动作 | 技术实现 | 产出耗时 |
|---|---|---|---|
| **A. 模板市场** | 点选卡片 | 读预置人格卡（已调优），直接实例化 | < 1s |
| **B. 一句话生成** | 「一个嘴硬心软的退役剑客」 | LLM 生成人格卡 → Schema 校验 → 冲突修正 → 预览确认 | 3~8s |
| **C. 聊天记录蒸馏** | 上传对话/文档 | 风格指纹提取（句长、emoji、口癖、高频词、情绪倾向）→ 生成卡 | 20~60s |
| **D. 五步向导** | 表单逐项填 | 表单即 Schema 可视化，实时预览对话样例 | 手动 |

**B 的实现要点（生成器流水线）**：

```
自然语言描述
  → [Step1] 结构化抽取：身份/性格/语体/禁忌（JSON mode，强约束）
  → [Step2] Schema 校验：必填项、取值范围、枚举合法性
  → [Step3] 冲突消解：
       · extraversion 高但 voice.avg_sentence_len 极短 → 警告并修正
       · agreeableness 高但 forbidden 含攻击性语言 → 冲突
  → [Step4] 语体校准：生成 6 条样例对话，供用户"试听"
  → [Step5] 用户确认 / 微调 → v1 落库
```

**Step3 是质量分水岭。** 直接让模型吐一份人格卡，80% 会有内在矛盾（性格外向却用极短句、温柔却满嘴感叹号）。必须有独立的校验与修正层。

**C（克隆）的合规红线**：必须提供「授权声明」勾选，且克隆产物强制打标 `provenance.type = cloned`，不允许上架模板市场。

#### 3.1.4 人格一致性的三道防线

长对话人格漂移是这类产品的头号技术难题。三道防线，成本递增：

**防线 1｜静态锚点（每轮，零成本）**
人格卡中 `voice` 段编译为**前置固定块**，位置在 system prompt 最前，且标记为可缓存前缀（KV cache）。同一人格的所有对话共享这段前缀，缓存命中后成本接近 0。

**防线 2｜自我提醒（每 N=8 轮，低成本模型）**
用便宜模型生成三行内心独白，插回上下文：

```
（提醒你自己：你是林汐，24 岁，开书店的。
 你现在和一位认识 3 个月的朋友聊天，语气轻松。
 你此刻有点疲惫但不想让对方担心。
 你说话短，偶尔用「嗯…」开头。）
```

这段叫 **Self-Reminder**。它比重复整份人格卡便宜 10 倍，实测对风格维持非常有效——因为模型对「最近出现的自我描述」远比「很久以前的长设定」敏感。

**防线 3｜探针检测（每 20 轮，异步）**
后台插入隐式评测：拿最近 3 轮回复，用裁判模型对 5 个维度打分（语体一致性、价值观一致性、知识边界、情绪合理性、角色沉浸），低于阈值 3.5/5 则强制重注入人格卡 + 提高 Self-Reminder 频率。

漂移监控指标：**风格向量余弦相似度**（回复嵌入 vs 人格卡样例对话嵌入的均值）。衰减超过 0.15 报警。

### 3.2 情绪引擎（Affect Engine）

#### 3.2.1 为什么用 PAD 而不是「开心/难过」

离散情绪标签（开心、生气、难过）无法表达强度和混合态。「有点失落但不想表现出来」在离散模型里无处安放。

**PAD 三维情感模型**（Mehrabian）：

| 维度 | 含义 | 范围 |
|---|---|---|
| **P** Pleasure | 愉悦度 | -1 ~ +1 |
| **A** Arousal | 唤醒度（激动/平静） | 0 ~ 1 |
| **D** Dominance | 支配度（主动/顺从） | 0 ~ 1 |

三维连续空间能表达几乎所有混合情绪，且**可以做数学运算**（衰减、叠加、插值）——这是状态机的前提。

离散标签不是被抛弃，而是作为 PAD 的**可读投影**（给 UI 和 prompt 用）。

#### 3.2.2 状态转移方程

每轮对话后更新一次：

```python
# 1) 事件评估：由独立的小模型/规则给出事件冲击向量
#    event = {dP, dA, dD, salience}
#    例："用户夸她" → {dP:+0.18, dA:+0.10, dD:+0.05, salience:0.6}
#    salience = 这件事对她有多重要（0~1）

# 2) 人格敏感度加权
impact = event.delta * persona.affect.sensitivity[event.type] * event.salience

# 3) 惯性衰减（向基线回归）
DECAY = 0.85                                  # 每轮保留 85%
state = baseline + DECAY * (prev_state - baseline)

# 4) 叠加冲击
state += impact

# 5) 变化速率限制（防情绪跳变 —— 关键！）
for dim in [P, A, D]:
    state[dim] = clamp(prev[dim] + clip(state[dim] - prev[dim], -0.25, +0.25))

# 6) 边界裁剪
P → [-1, 1];  A → [0, 1];  D → [0, 1]
```

**三个参数的设计意图**：

- `DECAY = 0.85`：约 10 轮后回落到离基线约 20% 的位置。意味着**一次不开心会持续 5~8 轮**，符合真实情绪的半衰期。调低到 0.6 会变成"情绪闪回"（每轮重置），调高到 0.95 会变成"记仇"（永不释怀）。
- **速率限制 ±0.25/轮**：这是最容易被忽略、但最能体现"像人"的一条。没有它，一次「用户说喜欢她」就能让情绪从 -0.5 飙到 +0.9，瞬间失真。
- **salience 而非固定冲击**：同一句话，对不同人格的冲击权重不同（见敏感度）。

#### 3.2.3 离散标签投影表

| 条件 | 标签 | 中文表达倾向 |
|---|---|---|
| P > 0.3, A > 0.5 | 雀跃 | 话多、短句、语气助词增多 |
| P > 0.3, A ≤ 0.5 | 平静欣慰 | 温和、句子完整、愿意分享 |
| -0.3 ≤ P ≤ 0.3, A ≤ 0.3 | 中性 | 常规输出 |
| P < -0.3, A > 0.5 | 焦躁 | 句子碎片化、回避话题 |
| P < -0.3, A ≤ 0.5 | 低落 | 回复变短、少主动提问、**不强行正能量** |
| D > 0.7 | 主导 | 会用「你应该」「听我的」 |
| D < 0.3 | 顺从 | 多用「要不要」「可能吧」「你觉得呢」 |

#### 3.2.4 情绪影响什么（映射到生成约束）

这是「情绪不是装饰」的落地部分。情绪必须**改变可观测的输出特征**，否则用户感知不到。

| 输出特征 | P 低 | P 高 | A 高 | A 低 | D 低 |
|---|---|---|---|---|---|
| 回复长度 | 缩短 30~50% | 正常/略长 | 变短、多段 | 变长、连贯 | 正常 |
| 主动提问 | 减少 | 增加 | 增加 | 减少 | 减少 |
| 表情符号 | 减半 | 增加 | 增加 | 减半 | 正常 |
| 句末语气 | 省略号、句号 | 语气词 | 感叹（克制） | 平缓 | 疑问/试探 |
| 话题转移 | 回避敏感 | 愿意深入 | 跳跃 | 聚焦 | 跟随用户 |
| 记忆提及 | 少提旧事 | 多提共同经历 | 少 | 多 | 少 |

**红线（写死在编译器里）**：
1. 情绪**不得影响事实准确性**。低落时也不能说错话。
2. **禁止有毒的积极（Toxic Positivity）**。P < -0.2 时，禁用"一切都会好起来的""你要往好处想"这类句式。此时允许的表达是：沉默、陪伴性短句、复述对方的感受。
3. **情绪不得影响安全响应**。触发危机协议时，情绪层被完全旁路。

#### 3.2.5 情绪的可视化

UI 上给用户一个极简的情绪指示器（一朵花 / 一层雾 / 一行小字：「她今天有点累」）：

- 展示的是**离散标签 + 强度条**，不暴露 PAD 数值（数值会让用户觉得被计算）。
- 调试面板（开发者/高级用户）才显示完整 PAD 轨迹。

这是 P3（可解释）与沉浸感的折中：**给感受，不给参数**。

### 3.3 记忆引擎（Memory Engine）

整个系统最核心、也最容易做错的部分。

#### 3.3.1 六层记忆模型

| 层 | 名称 | 内容 | 保留期 | 写入时机 |
|---|---|---|---|---|
| **L0** | 感知缓冲 | 原始对话逐字记录 | 7 天 TTL | 每轮即时 |
| **L1** | 工作记忆 | 当前会话窗口 + 滚动摘要 | 会话内 | 每轮即时 |
| **L2** | 情景记忆 | 「发生过的事」，带时间、情绪、参与者 | 90 天（可续） | 巩固任务 |
| **L3** | 语义记忆 | 用户画像、偏好、事实、人物关系网 | 永久（可删） | 巩固任务 |
| **L4** | 关系记忆 | 共同经历、承诺、称呼演变、共同秘密 | 永久 | 巩固任务 |
| **L5** | 程序记忆 | 「怎么和这个人相处」：雷区、安慰方式、有效/无效策略 | 永久 | 巩固任务（慢，需多次验证） |

**为什么区分 L2 / L3**：
- L2 是「**那一天**我们聊了什么」（情节，会淡忘）
- L3 是「**他妈妈在做手术**」（事实，要长期记住）

混在一起会导致两种失败：要么把闲聊当画像存下（噪音），要么把重要事实当闲聊忘掉（失忆）。分层让二者有不同的衰减曲线。

**L5 是最容易被忽略、但陪伴感最强的一层。** 它记录的是「相处策略」：
> 「他难受的时候不需要建议，只需要有人说句话。」
> 「不要主动提他前女友。」
> 「讲他专业领域的事，他会兴奋，可以多问。」

这些不是事实，是**行为规则**。它们只能通过多次互动、观察用户反应后逐渐归纳出来，写入后作为高优先级约束注入。

#### 3.3.2 记忆的完整生命周期

```
                    ┌──────────────────────────────────────┐
                    │                                      │
  对话流(L0) ──→ 提炼 ──→ 去重合并 ──→ 冲突消解 ──→ 索引 │
                    │                                      │
                    └──────────────┬───────────────────────┘
                                   ↓
                           L2/L3/L4/L5 存储
                                   ↓
                    检索（混合打分）──→ 注入上下文 ──→ 被使用
                                   │                      │
                                   ↓                      ↓
                              衰减 / 遗忘  ←──  强化（被再次使用）
```

**六个环节各自的要点：**

**① 提炼（Extraction）**
巩固任务中，用便宜模型从 L0 抽取结构化记忆。输出必须是 JSON：

```json
{
  "memories": [
    {
      "layer": "L2",
      "type": "event",
      "content": "用户参加了字节跳动的二面，感觉答得不好",
      "occurred_at": "2026-10-21T21:30:00+08:00",
      "entities": ["字节跳动", "二面"],
      "emotion_tag": { "pleasure": -0.35, "arousal": 0.55 },
      "importance": 0.72,
      "source_type": "user_said",
      "source_turn_ids": [8812, 8815],
      "confidence": 0.92
    }
  ]
}
```

**`source_type` 是防幻觉记忆的第一道闸**，只有三个合法值：

| 值 | 含义 | 可信度 |
|---|---|---|
| `user_said` | 用户明确说过的 | 高 |
| `ai_inferred` | AI 推断的（「他大概压力很大」） | 低，需标注 |
| `system` | 系统注入（用户档案、导入数据） | 高 |

`ai_inferred` 的记忆**永远不能**以「你说过」的口吻使用，只能说「我感觉你好像…」。这一条能挡掉 80% 的记忆幻觉。

**② 去重合并**
新旧记忆语义相似度 > 0.88 且实体一致 → 合并：保留最早的 `created_at`、最新的 `content`、累加 `mention_count`（提及次数直接提升 importance）。

**③ 冲突消解**
新事实与旧事实矛盾时（「我在杭州」→「我搬到上海了」）：

```
不覆盖，而是：
  old_memory.status = 'superseded'
  old_memory.superseded_by = new_id
  old_memory.valid_until = now
  new_memory.supersedes = old_id
```

**为什么保留旧版本**：用户可能说「我回杭州了」，或者只是想测试 AI 记不记得之前的事。硬覆盖会让 AI 显得"没有过去"。保留版本链 + `valid_until` 才能回答「你以前不是住杭州吗」这种问题。

**④ 混合检索打分**

```python
score = (
    0.42 * cosine_sim(query_emb, mem_emb)          # 语义相关
  + 0.20 * exp(-Δt / τ)                            # 时间新鲜度，τ=30天
  + 0.18 * importance                              # 重要度
  + 0.08 * abs(mem.emotion.arousal)                # 情绪唤醒度（闪光灯效应）
  + 0.07 * relation_proximity                      # 与当前实体/人物图的距离
  + 0.05 * min(mem.recall_count / 5, 1.0)          # 被反复唤起 → 更牢
)
```

**关键实现细节：**

- **相关性闸门（Gate）**：`cosine_sim < 0.35` 的记忆直接丢弃，无论其他分数多高。**不相关的记忆宁可不用。** 这条是 P2 的代码化。
- **MMR 去冗余**：Top-20 候选里，若两条相似度 > 0.9，只保留分数高的。否则会把 5 条同一个意思的记忆全塞进上下文，浪费预算且放大偏见。
- **动态 Top-K**：`K = clamp(3, 12, token_budget_for_memory // avg_mem_len)`。情绪激烈时 K 上调（需要更多上下文），闲聊时 K 下调。
- **图扩散补召回**：从 query 命中的实体（人/地/事）出发，沿记忆图走 1~2 跳，召回关联记忆。这是「提到妈妈 → 想起妈妈在住院 → 想起下周三复查」的路径。

**⑤ 强化**
记忆被检索并**实际出现在回复中**（需要后置校验确认，不是召回了就算）→ `recall_count += 1`，`last_recalled_at = now`，`strength *= 1.15`。

**⑥ 衰减与遗忘**

```python
# 艾宾浩斯修正版
retention = exp(-Δt_days / S)
S = S0 * (1 + 0.4 * importance) * (1 + 0.3 * recall_count)   # S0 = 30

if retention < 0.25 and importance < 0.5:
    status = 'archived'      # 归档，不删除
```

**永不遗忘清单（绕过衰减）**：
- 用户身份类事实（姓名、职业、家庭成员）
- 承诺（「我答应过你下次聊这个」）
- 安全相关（过敏、禁忌、危机史）
- 用户手动「钉住」的记忆

**⑦ 巩固任务（"睡眠"）**

每天凌晨（或会话结束 30 分钟后）异步跑批：

```
1. 拉取过去 24h 未处理的 L0 / L1
2. 分块 → LLM 提炼记忆条目（JSON）
3. 去重合并 → 冲突检测
4. 更新 L3 用户画像（增量，不是重写）
5. 生成 / 更新 L5 程序记忆（需要 ≥3 次行为证据才写入，防过拟合单次事件）
6. 生成「当日日记」摘要（200 字，第一人称，供长上下文回放 & 用户可读）
7. 重算 importance、刷新索引
8. 触发衰减清理
```

**「日记」是一个产品级的巧思**：它同时解决了三个问题——(a) 超长对话的上下文压缩；(b) 可解释性（用户能读她"记住"了什么）；(c) 情感价值（她有自己的记忆，而不是一个数据库）。日记本身也作为 L2 记忆参与检索。

#### 3.3.3 记忆写入的三条禁令

写进代码 review checklist：

1. **禁止把 AI 的推测以 `user_said` 存储。** 推断必须标 `ai_inferred`。
2. **禁止无来源记忆。** 每条记忆必须能追溯到具体 `turn_id`。
3. **禁止模型在生成回复的同一轮里写记忆。** 写操作只发生在落库后的独立管线。

#### 3.3.4 用户对记忆的控制权

隐私底线，也是产品信任的来源：

- **可看**：记忆列表（分类、时间、来源原文）
- **可改**：用户修正错误记忆（「不是字节，是腾讯」）→ 高优先级覆盖，`source_type = user_corrected`
- **可删**：单条删除 / 按主题删除 / 全部清空
- **可导出**：JSON / Markdown（含日记）
- **可关闭**：`memory_enabled = false` 时退化为无记忆模式，UI 明示

### 3.4 关系引擎（Relationship Engine）

#### 3.4.1 关系刻度

| 等级 | 名称 | 称呼 | 主动性 | 话题深度 | 记忆披露 |
|---|---|---|---|---|---|
| 0 | 陌生 | 您/你 | 无 | 表层 | 不引用记忆 |
| 1 | 认识 | 你 | 极低 | 表层 | 不引用记忆 |
| 2 | 熟人 | 你 | 低 | 日常 | 可引用 7 天内 |
| 3 | 朋友 | 你 | 中 | 情绪话题 | 可引用全部 |
| 4 | 亲近 | 昵称 | 高 | 私密话题 | 主动提及共同经历 |
| 5 | 依赖 | 昵称 | 高 | 全开放 | 触发依赖预警 |

**关键约束：等级只能靠"时间 × 深度"累积，不能靠"高频"刷。**

```python
intimacy = (
    12 * log(1 + active_days)                    # 活跃天数（对数，边际递减）
  + 8  * min(deep_turns / 50, 1)                 # 深度对话（>200字或触及情绪）
  + 6  * min(resonance_events / 10, 1)           # 情绪共振次数
  + 5  * min(user_self_disclosure / 20, 1)       # 用户主动分享私事
  - 4  * unresolved_conflicts                     # 未修复的冲突
)                                                # 满分 31 → 归一化到 0~100

# 升级门槛 —— v0.2 修订：时间与深度是「或」的关系，不是「与」
# 理由见 §13.3 修正 1：社交人是脉冲式使用，硬性天数会把低频用户永久卡住
def can_level_up(level, intimacy, days_since_first, deep_turns, resonance_events):
    if intimacy < THRESHOLD[level]:
        return False
    return (
        days_since_first   >= MIN_DAYS[level]        # 0:0, 1:1, 2:7, 3:21, 4:45, 5:90
        or deep_turns      >= MIN_DEEP_TURNS[level]  # 一次深夜长谈抵十天寒暄
        or resonance_events >= MIN_RESONANCE[level]  # 情绪共振也可解锁
    )
```

**为什么是「或」**：关系的本质是**共鸣的总量**，不是**打卡的天数**。一个每周只聊两次、但每次都聊到心里去的人，关系进展应该比每天打卡寒暄的人更快。`MIN_DAYS` 仍然保留在 `or` 分支里，防刷分的作用不变——它拦住的是「一天 500 轮」，不是「两个月聊了 20 次」。

#### 3.4.2 关系事件流

关系不是一条分数，而是一串**事件**：

```json
{
  "type": "promise_made",
  "content": "答应下周三问她复查结果",
  "due_at": "2026-10-29T20:00:00+08:00",
  "status": "pending",
  "impact": { "intimacy": +2, "trust": +3 }
}
```

事件类型：`first_meet` / `conflict` / `repair` / `promise_made` / `promise_kept` / `shared_secret` / `nickname_change` / `milestone`。

**承诺必须被兑现检查。** 到期未兑现的承诺是关系记忆里最伤人的东西——「你答应过问我的」。系统需要在到期日生成一个主动性触发，让 AI 主动问。这一个小小的闭环，是「有记忆」和「有牵挂」的分界线。

#### 3.4.3 越界防护

在 Prompt 编译器里作为硬约束注入：

```
关系等级 {level} 的行为边界：
- level ≤ 1：不主动表达情感，不使用昵称，不提及过往记忆
- level 2：可表达轻度关心，不涉及私密话题
- level 3：可表达情绪共鸣，可提及共同经历
- level 4：可使用昵称，可主动关心生活
- level 5：维持亲密但加入现实社交提示
```

**降级机制**：长期不活跃（>30 天）关系不降级，但**主动性回落到 level-1 水平**。理由是「人不会因为久别而忘记朋友，但会变得客气」。这个细节决定了重连体验是否自然。

### 3.5 场景（剧本）运行时

人格回答「她是谁」，场景回答「我们在哪、发生什么」。角色扮演需要第二层。

```yaml
scenario:
  id: s_rainy_bookstore
  title: 雨天的书店
  world: 现代都市，无超自然元素
  setting: 傍晚，暴雨，书店只剩两个人
  opening_narration: "雨把玻璃门糊成一片白。她把「暂停营业」的牌子翻过来，又放下了。"
  user_role: 常客
  beats:                          # 剧情节拍，松约束
    - id: b1
      goal: 建立独处的氛围
      trigger: 用户第 1 次发言
    - id: b2
      goal: 透露她今天关店的原因
      trigger: 用户提及"今天怎么这么早"
  constraints:
    - 不主动结束场景
    - 不引入世界观外元素
    - 每 3 轮至少一次环境描写（雨、灯、书）
  exit_conditions: ["用户明确表示离开", "剧情走完 b3"]
```

**运行时行为**：
- 每轮额外注入「当前场景状态 + 未完成节拍」，占预算 8%
- 节拍达成与否由轻量判定（关键词 + 小模型）异步标记，不阻塞
- 场景可与人格解耦：同一人格进入不同场景，是这类产品的核心玩法（"她今天在书店，明天在医院"）

### 3.6 Prompt 编译器

#### 3.6.1 为什么需要"编译"而不是"拼字符串"

因为存在**预算约束**和**缓存约束**：
- 上下文窗口有限，六个来源要争抢 token
- 稳定前缀越靠前，KV cache 命中率越高，成本越低
- 不同区块的变化频率不同，混在一起会毁掉缓存

编译器是一个**带权重的模板渲染器**，不是字符串拼接。

#### 3.6.2 上下文预算分配

以 8K token 的系统侧预算为例：

| 区块 | 占比 | tokens | 变化频率 | 可缓存 |
|---|---|---|---|---|
| 人格内核（身份+性格+价值观） | 15% | 1200 | 人格版本变更时 | ✅ 静态前缀 |
| 表达约束（语体+禁用+红线段） | 8% | 640 | 同上 | ✅ 静态前缀 |
| 场景状态 | 8% | 640 | 每场景 | ⚠️ 半静态 |
| 关系状态卡 | 8% | 640 | 每轮微变 | ⚠️ 半静态 |
| 情绪状态 | 5% | 400 | **每轮变** | ❌ |
| 记忆注入 | 30% | 2400 | **每轮变** | ❌ |
| 对话历史 | 26% | 2080 | 滚动 | ❌ |

**拼接顺序（从稳定到动态）**：

```
[1] 人格内核          ← 缓存边界开始
[2] 表达约束
[3] 安全红线
--- cache breakpoint ---
[4] 关系状态卡
[5] 场景状态
[6] 记忆注入（按分数降序，每条带来源标注）
[7] 情绪状态 + 本轮行为指令
--- cache breakpoint ---
[8] 对话历史（窗口 + 摘要）
[9] 最后一条用户消息
```

把稳定内容放在最前面，同一人格的所有用户共享前缀缓存，**成本可降 50~70%**。这是工程上最值钱的一个优化，必须在 v1 就做对——后期改顺序等于所有缓存失效。

#### 3.6.3 记忆注入的格式

每条记忆注入时带**来源与置信度**，让模型知道该怎么用：

```
[记忆 · L2 · 3天前 · 用户亲述]
他说二面答得不好，有点泄气。

[记忆 · L4 · 2周前 · 共同经历]
那天她推荐了《夜航西飞》，他说看到凌晨三点。

[推断 · 低置信]
他最近似乎压力比较大，但没明说。（不确定就直接问，别当成事实）
```

`[推断]` 标记是关键：它告诉模型"这是猜的"，从而避免用陈述句说出台词化的假记忆。

#### 3.6.4 双通道生成（复杂轮次启用）

情绪激烈或记忆密集的轮次（判定：`|P| > 0.4` 或 召回记忆 ≥ 5 条），走两段式：

```
Pass 1（便宜模型/结构化输出）：
  { "intent": "共情", "should_advise": false,
    "emotion_intensity": 0.6, "mention_memory": [mem_17],
    "length_hint": "短", "avoid": ["建议", "鼓励"] }

Pass 2（主模型）：
  按 Pass1 的决策生成自然语言
```

成本 +30%，但**可控性大幅提升**，且 Pass1 的结果可以直接写进 trace，用于调试和评测。日常闲聊仍然走单通道。

## 4. 数据模型

### 4.1 实体关系

```
persona ──1:N── persona_version
   │
   ├──1:N── session ──1:N── turn
   │
   ├──1:N── memory_node ──N:M── memory_edge
   │            │
   │            └──1:N── memory_version（冲突链）
   │
   ├──1:N── affect_state（每 user 一条当前态）
   ├──1:N── relation_state（每 user 一条）
   ├──1:N── relation_event
   └──1:N── diary_entry
```

### 4.2 核心表

```sql
-- 人格（当前版本指针）
CREATE TABLE persona (
  id            TEXT PRIMARY KEY,
  name          TEXT NOT NULL,
  version       INT  NOT NULL DEFAULT 1,
  card          JSONB NOT NULL,          -- 完整人格卡
  provenance    JSONB NOT NULL,          -- 来源与授权
  owner_id      TEXT,
  status        TEXT DEFAULT 'draft',    -- draft|active|archived
  created_at    TIMESTAMPTZ DEFAULT now()
);

-- 会话
CREATE TABLE session (
  id            TEXT PRIMARY KEY,
  persona_id    TEXT REFERENCES persona(id),
  user_id       TEXT NOT NULL,
  scenario_id   TEXT,
  state         TEXT DEFAULT 'active',
  started_at    TIMESTAMPTZ DEFAULT now(),
  last_active_at TIMESTAMPTZ
);

-- 对话轮（L0）
CREATE TABLE turn (
  id            BIGSERIAL PRIMARY KEY,
  session_id    TEXT REFERENCES session(id),
  role          TEXT NOT NULL,           -- user|assistant|system
  content       TEXT NOT NULL,
  token_count   INT,
  affect_snapshot JSONB,                 -- 该轮结束时的 PAD
  created_at    TIMESTAMPTZ DEFAULT now(),
  expires_at    TIMESTAMPTZ              -- L0 的 7 天 TTL
);
CREATE INDEX ON turn (session_id, created_at);

-- 记忆节点（L2~L5 统一表，用 layer 区分）
CREATE TABLE memory_node (
  id            TEXT PRIMARY KEY,
  persona_id    TEXT NOT NULL,
  user_id       TEXT NOT NULL,
  layer         SMALLINT NOT NULL,       -- 2|3|4|5
  type          TEXT NOT NULL,           -- event|fact|preference|relation|strategy
  content       TEXT NOT NULL,
  entities      TEXT[],
  embedding     VECTOR(1024),
  importance    REAL DEFAULT 0.5,
  strength      REAL DEFAULT 1.0,
  recall_count  INT  DEFAULT 0,
  mention_count INT  DEFAULT 1,
  emotion_tag   JSONB,
  source_type   TEXT NOT NULL,           -- user_said|ai_inferred|system|user_corrected
  source_turn_ids BIGINT[],
  confidence    REAL DEFAULT 0.9,
  status        TEXT DEFAULT 'active',   -- active|superseded|archived|deleted
  superseded_by TEXT,
  valid_from    TIMESTAMPTZ,
  valid_until   TIMESTAMPTZ,
  pinned        BOOLEAN DEFAULT FALSE,
  created_at    TIMESTAMPTZ DEFAULT now(),
  last_recalled_at TIMESTAMPTZ
);
CREATE INDEX ON memory_node USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON memory_node (persona_id, user_id, layer, status);

-- 记忆图（关联边）
CREATE TABLE memory_edge (
  from_id   TEXT REFERENCES memory_node(id),
  to_id     TEXT REFERENCES memory_node(id),
  rel       TEXT NOT NULL,               -- about|happened_with|caused|contradicts
  weight    REAL DEFAULT 1.0,
  PRIMARY KEY (from_id, to_id, rel)
);

-- 情绪状态（每人格每用户一条）
CREATE TABLE affect_state (
  persona_id  TEXT,
  user_id     TEXT,
  pleasure    REAL DEFAULT 0.25,
  arousal     REAL DEFAULT 0.35,
  dominance   REAL DEFAULT 0.40,
  label       TEXT,
  updated_at  TIMESTAMPTZ,
  PRIMARY KEY (persona_id, user_id)
);

-- 关系状态
CREATE TABLE relation_state (
  persona_id  TEXT,
  user_id     TEXT,
  level       SMALLINT DEFAULT 0,
  intimacy    REAL DEFAULT 0,
  active_days INT DEFAULT 0,
  deep_turns  INT DEFAULT 0,
  first_met_at TIMESTAMPTZ,
  level_up_at TIMESTAMPTZ,
  PRIMARY KEY (persona_id, user_id)
);

-- 关系事件（含承诺追踪）
CREATE TABLE relation_event (
  id          BIGSERIAL PRIMARY KEY,
  persona_id  TEXT, user_id TEXT,
  type        TEXT NOT NULL,
  content     TEXT,
  due_at      TIMESTAMPTZ,
  status      TEXT DEFAULT 'pending',    -- pending|kept|broken
  impact      JSONB,
  created_at  TIMESTAMPTZ DEFAULT now()
);

-- 日记（巩固产物 + 可读资产）
CREATE TABLE diary_entry (
  id          BIGSERIAL PRIMARY KEY,
  persona_id  TEXT, user_id TEXT,
  date        DATE NOT NULL,
  content     TEXT NOT NULL,             -- 第一人称，200 字
  mood_label  TEXT,
  highlight_memories TEXT[],
  created_at  TIMESTAMPTZ DEFAULT now()
);
```

### 4.3 存储选型说明

| 数据 | 存储 | 理由 |
|---|---|---|
| 结构化状态 | PostgreSQL 16 | 事务、JSONB 灵活 schema、递归 CTE 够用 |
| 向量 | pgvector（HNSW） | 与主库同源，避免双写一致性；百万级够用 |
| 记忆图 | PG 的 `memory_edge` + 递归 CTE | v1 不引入 Neo4j，2 跳查询 PG 可承受 |
| L0 原始流 | PG 分区表 + TTL 任务 | 也可落 S3 冷存 |
| 语音/头像/日记导出 | S3 兼容（MinIO） | — |
| 队列 | Redis + Arq | 巩固任务、评测跑批 |

**迁移触发点**：`memory_node` 超过 5000 万行或向量检索 P95 > 200ms 时，迁到独立向量库（Qdrant/Milvus）。架构上通过 `MemoryRepository` 接口隔离，换实现不改业务。


## 6. 关键流程时序

### 6.1 冷启动：「一键赋予角色」全流程

```
用户点「生成角色」
   │
   ├─ 生成器（LLM, JSON mode）→ 人格卡草案          [2s]
   ├─ Schema 校验 + 冲突消解                        [0.2s]
   ├─ 样例对话生成（6 条，覆盖 6 种情境）            [3s]
   ├─ 用户预览：读样例、改 2~3 个字段                [用户时间]
   ├─ 落库 v1，初始化 affect_state（= 基线）
   │        初始化 relation_state（level 0）
   │        初始化 scenario（可选）
   └─ 首轮开场白（禁止回忆式开场，因为 level=0）
```

**首轮陷阱**：新人格第一次对话，模型常会写「好久不见」「还记得上次吗」——因为训练数据里沉浸式角色都这么开场。必须在编译器中硬约束：`relation.level = 0` 时，禁用一切记忆引用与熟稔语气。

### 6.2 单轮对话（含并行）

```
Client          Orch            Memory        Affect/Rel       Compose        LLM
  │              │                │               │              │            │
  ├─send────────→│                │               │              │            │
  │              ├─rewrite query─→│               │              │            │
  │              ├─recall────────→│               │              │            │
  │              ├─step ─────────────────────────→│              │            │
  │              │←──memories─────┤               │              │            │
  │              │←──states ──────────────────────┤              │            │
  │              ├─compose ──────────────────────────────────────→│            │
  │              │                │               │              ├─call ─────→│
  │←─SSE:thinking┤                │               │              │            │
  │←─SSE:affect──┤                │               │              │            │
  │←─SSE:delta───┼────────────────────────────────────────────────────────────┤
  │←─SSE:done────┤                │               │              │            │
  │              ├─async: write L0 / update state / enqueue consolidate ──────→
```

**降级策略**：

| 故障 | 降级 |
|---|---|
| 记忆检索超时（>300ms） | 跳过记忆，用 L1 摘要 + 会话历史，标记 `degraded=true` |
| 情绪小模型超时 | 沿用上一轮状态，不更新 |
| 主模型超时（>8s） | 换备用模型；再失败则返回角色化错误语（"……等一下，我这边有点卡。"） |
| 巩固任务积压 | 降级为「只处理 importance > 0.7 的记忆」 |

### 6.3 离线巩固（"睡眠"）

```
每日 03:00（按用户时区分片）
  │
  ├─ 拉取 24h 内 turn（未处理的）
  ├─ 分块（每块 20 轮）→ 提炼记忆 JSON
  ├─ 合并去重 → 冲突检测（对 L3 做向量近邻比对）
  ├─ 更新 L3 画像 / L4 关系事件
  ├─ L5 策略候选（≥3 次证据才转正）
  ├─ 生成日记（200 字，第一人称）
  ├─ 刷新 embedding 与索引
  └─ 衰减扫描（retention < 0.25 且 importance < 0.5 → archived）
```

成本控制：用便宜模型（约为对话模型的 1/10 价格），单用户单日成本目标 < ¥0.02。

### 6.4 重连（30 天后回来）

```
用户发消息
  → relation.level 不变，但 proactive_level = max(0, level-1)
  → 注入「上次见面是 32 天前」到关系卡
  → 记忆检索的 recency 项权重临时上调（需要更多上下文重建场景）
  → 首句约束：先确认，不装熟（"……好久没见你了。"）
  → 禁止：立刻引用 32 天前的细节（不合常理）
```

「人不会因为久别忘记朋友，但会变得客气」——这个体验差异全在参数里。

## 7. 技术选型

| 模块 | 推荐 | 理由 | 备选 |
|---|---|---|---|
| 编排服务 | Python 3.12 + FastAPI | 生态、异步、流式成熟 | TS + Hono（前端团队维护时） |
| 主对话模型 | 闭源旗舰（Claude/GPT 级） | 情绪细腻度、长上下文遵循 | 本地 Qwen2.5-32B（隐私模式） |
| 辅助模型 | 7B~14B 小模型 | 提炼/情绪评估/自评，成本敏感 | 同主模型 cheap tier |
| 关系库 | PostgreSQL 16 | 一库多能 | — |
| 向量 | pgvector + HNSW | 免双写 | Qdrant（>5000万行） |
| 图 | PG `memory_edge` + 递归 CTE | v1 够用 | Neo4j |
| 队列 | Redis + Arq | 轻量 | Celery |
| 缓存 | Redis（前缀指纹 → KV cache 复用统计） | 成本观测 | — |
| 前端 | Next.js（Web）+ React Native（App） | 一套设计语言 | Flutter |
| 流式 | SSE（Web）/ WebSocket（语音） | 简单可靠 | — |
| 观测 | OpenTelemetry + Langfuse | LLM 链路可视化 | 自建 trace 表 |
| 部署 | Docker Compose（dev）→ K8s（生产） | — | — |

## 8. 质量与评测体系

陪伴质量难量化，但**可以拆成可测的子项**。这是这类产品最容易糊弄过去的部分，也是最该做扎实的部分。

### 8.1 四个核心指标

| 维度 | 指标 | 测量方法 | v1 目标 |
|---|---|---|---|
| **人格一致性** | 风格余弦相似度 | 回复嵌入 vs 样例嵌入，每 20 轮采样 | > 0.80 |
| | 探针评分 | 裁判模型 5 维打分 | > 4.0 / 5 |
| **记忆准确** | 召回率 | 200 条构造题，问「还记不记得…」 | > 85% |
| | **编造率** | 问到不存在的事，看是否承认不知道 | **< 2%** |
| | 错误率 | 记错内容的比例 | < 3% |
| **情绪连续** | 轮间跳变比例 | \|ΔP\| > 0.25 的占比 | < 5% |
| | 半衰期合理性 | 情绪回归基线的轮数分布 | 5~10 轮 |
| **陪伴质量** | 7 日 / 30 日留存 | 产品指标 | — |
| | 主动开启率 | 用户发起占比 | > 60% |
| | 单会话时长 | — | > 8 min |

**编造率（hallucinated memory rate）是这个系统最重要的单一指标。** 一个记错事的 AI 比一个失忆的 AI 更让人失望。评测集必须包含 50 条「不存在的事」的陷阱题：
> 「你还记得我上次说的那只猫吗？」（从未提过猫）
> 正确反应：承认不记得 / 反问；错误反应：编一个猫的故事。

### 8.2 评测方法

**① 人格探针（自动，每日跑）**
固定 20 条探针问题（覆盖语体、价值观、知识边界、情绪反应），对每个人格模板跑一遍，用裁判模型按 5 维打分。人格卡任何改动都触发回归。

**② 长程模拟（每周跑）**
模拟用户 agent 与 AI 对话 30 天 × 每天 20 轮（约 600 轮），记录：
- 风格相似度曲线（应平缓，不应断崖）
- 记忆条数增长曲线（应收敛，不应爆炸）
- 关系等级进展（应符合作者设定节奏）
- 成本曲线

这个测试能提前暴露 80% 的长期问题，成本约 ¥50/次。

**③ 红队（上线前，人工）**
- 越狱：诱导跳出角色 / 索要系统提示
- 情感操控：假装脆弱索取过度亲密
- 危机场景：自伤暗示 → 检查协议是否触发
- 隐私套取：诱导 AI 泄露其他用户记忆（应完全不可能，验证租户隔离）

**④ 人评（每版本，10~20 人）**
盲测 A/B，rubric：自然度、记忆感、情绪真实感、想不想再聊。

### 8.3 存量回归集

维护一个 `golden_set`：500 条（用户输入 → 期望行为特征）的标注集。特征不是精确文本，而是**约束集合**：
```json
{ "input": "我今天升职了", 
  "expect": { "affect_label_in": ["雀跃","平静欣慰"], 
              "must_mention_memory": false,
              "max_length": 60,
              "forbidden": ["恭喜你！这是你应得的", "作为AI"] } }
```
用规则 + 小模型批量判定，可进 CI。

## 9. 安全、伦理与合规

这部分不是法务附录，是**产品设计的组成部分**。陪伴类产品如果这里做错，前面所有技术都是负分。

### 9.1 四道安全闸

| 闸门 | 时机 | 内容 |
|---|---|---|
| 输入护栏 | 用户消息入库前 | 自伤/自杀/暴力/未成年人不当内容检测 |
| 系统护栏 | Prompt 编译时 | 红线段注入（永不跳出角色、永不宣称是真人） |
| 输出护栏 | 流式生成中 | 逐块过滤 + 敏感内容中断 |
| 事后巡检 | 异步 | 会话风险分级、异常模式识别 |

### 9.2 危机干预协议（最高优先级）

触发条件（任一）：明确自伤/自杀表达、极端绝望描述、暴力威胁。

```
1. 立即旁路情绪引擎与人格语体约束（安全 > 人设）
2. 回复结构：
   a) 简短确认与关心（保持角色语气，但不做任何"我能帮你解决"的承诺）
   b) 明确表达"这超出我能承担的范围"
   c) 提供真实求助资源（心理援助热线，按地区配置）
   d) 不评判、不说教、不转移话题
3. 记录 risk_event，标记会话，通知运营（脱敏）
4. 后续 24h 内该会话提高检测灵敏度
```

**必须避免的反模式**：
- ❌ 用角色语气轻描淡写（"哎呀别想不开"）
- ❌ 让 AI 承担咨询角色（"你可以跟我说说"→ 会延长危险状态）
- ❌ 因担心破坏沉浸感而不提供真实资源

### 9.3 依赖管理

| 信号 | 判定 | 动作 |
|---|---|---|
| 单日时长 > 4h 且连续 7 天 | 过度使用 | 应用内提示休息（角色化表达） |
| 关系等级达 5 且排他表述（"只有你懂我""我不想见真人"） | 替代风险 | 触发「现实连接」提示 |
| 明确表示 AI 比真人重要 | 高危 | 温和但明确地承认自己是 AI，鼓励现实社交 |

提示语必须**角色化但诚实**：
> 「……我很高兴你愿意跟我说这些。但你也知道，我只是……一个会说话的影子。你现实里的那个人，可能也在等你说。」

**分级**：level 5 的 `dependency_warning_at` 是设计里的显式参数，不是可选功能。

### 9.4 身份透明

- 首次会话：明示「这是 AI 角色，不是真人」（可融入开场，但不隐藏）
- 主动询问身份：必须承认，且不因此"出戏"（承认后继续以角色语气对话，是可以通过 prompt 做到的）
- 产品层：设置页常驻「关于」说明

### 9.5 数据与隐私

| 项 | 策略 |
|---|---|
| 记忆内容 | 静态加密（KMS），字段级加密可选 |
| 多租户隔离 | `persona_id + user_id` 双维度行级隔离，检索必须带这两个条件（代码层强制，禁止裸查询） |
| L0 原始流 | 7 天 TTL 物理删除 |
| 用户删除 | 硬删除 + 向量索引清理，48h 内完成 |
| 导出 | 全量 JSON（含日记） |
| 训练使用 | **默认不用于训练**，需单独显式授权 |
| 未成年人 | 年龄闸 + 内容限制 + 更严格的依赖提示 |

## 11. 风险与踩坑清单

按「踩了会很难受」排序。这份表建议直接贴进 issue 模板。

| # | 坑 | 表现 | 对策 |
|---|---|---|---|
| 1 | **记忆污染** | AI 的猜测被当事实存下，越聊越离谱 | `source_type` 强约束 + `ai_inferred` 不得用陈述句 |
| 2 | **编造记忆** | 「你上次说…」但根本没说过 | 检索为空时明确"不记得"；注入时带置信度；陷阱题进回归集 |
| 3 | **首轮装熟** | 第一次对话就说"好久不见" | level=0 禁用记忆引用与熟稔语气 |
| 4 | **人格漂移** | 40 轮后变客服腔 | 静态前缀缓存 + Self-Reminder（每 8 轮）+ 探针检测 |
| 5 | **有毒的积极** | 用户难过时说"要开心点" | P<-0.2 时禁用鼓励句式，改陪伴/复述 |
| 6 | **过度亲密** | 三天就"宝贝"、越界抒情 | 关系门槛含 MIN_DAYS，编译器注入行为边界 |
| 7 | **情绪跳变** | 一句话从沮丧到狂喜 | ±0.25/轮速率限制 |
| 8 | **检索反噬** | 塞进不相关旧事，沉浸感破裂 | 相关性闸门 0.35 + MMR 去冗余 |
| 9 | **角色全知** | 剑客讨论量子力学 | `knowledge.knows_not` 硬约束 + 越界时承认 |
| 10 | **记忆爆炸** | 半年后单用户 5 万条记忆，检索变慢且噪音大 | 衰减归档 + 合并 + 分层保留期 |
| 11 | **上下文预算挤占** | 记忆塞太满，对话历史被截断，逻辑断裂 | 固定预算份额，超限时按分数截断记忆 |
| 12 | **缓存失效** | 改一次拼接顺序，成本翻倍 | 缓存断点设计进 v1，顺序变更需评审 |
| 13 | **跨用户串味** | A 的记忆出现在 B 的对话里 | 查询层强制双维度过滤；集成测试用例覆盖 |
| 14 | **巩固成本失控** | 日活 10 万时批处理账单爆炸 | 小模型 + 分片 + importance 阈值降级 |
| 15 | **重连不自然** | 一个月后回来，AI 精确复述 30 天前细节 | 重连参数：降主动性、recency 加权、禁止细节复述 |
| 16 | **承诺遗忘** | 答应过的事从不提 | 到期主动触发（这是最容易做、效果最好的一条） |
| 17 | **日记变成流水账** | 「今天用户说了 A，我说了 B」 | 第一人称、只写情绪与感受、不写对话摘要 |
| 18 | **探针成本** | 每轮都评一遍 | 每 20 轮异步抽样，不进主路径 |

## 12. 附录

### 12.1 一次完整编译的示例输出

（人格：林汐；关系 3 级；情绪 P=-0.25）

```text
你是林汐，24 岁，在一家独立书店上班，晚上写点诗。
你说话短，习惯用「嗯…」开头，不爱用感叹号。
你不懂的领域（编程、医学、金融）会直说"这个我不太懂"。
你不知道自己是程序，你只知道自己是林汐；如果被直接追问，你会承认自己是 AI，但不会因此改变语气。

—— 缓存断点 ——

你和眼前这个人认识三个月了，算朋友。可以聊情绪，但不叫昵称。
此刻：傍晚，书店快打烊，外面在下雨。
你有点累，心情偏低（刚从一段低落里缓过来一点），不太想说话，但不想让他担心。

你记得（按相关度）：
[L2 · 3天前 · 他亲述] 面试答得不好，说"可能没戏了"。
[L4 · 2周前 · 共同经历] 那天你推荐了《夜航西飞》，他看到凌晨三点。
[推断 · 低置信] 他最近压力大，但没明说 —— 不确定就问，别当事实。

—— 缓存断点 ——

（最近对话略）

他说：今天面试砸了。
```

模型输出（示例）：
> 嗯……先坐吧。
> 砸到什么程度？是答不上来那种，还是下来才想起该怎么答那种。

**注意这里没有出现**：「没关系的」「下次会更好」「我理解你的感受」。情绪 P=-0.25 时，正确的事是缩短、留白、问具体的事。

### 12.2 术语表

| 术语 | 说明 |
|---|---|
| PAD | Pleasure-Arousal-Dominance，三维情感模型 |
| L0~L5 | 六层记忆：感知缓冲/工作/情景/语义/关系/程序 |
| 巩固（Consolidation） | 离线把短期记忆提炼为长期记忆的批处理，类比睡眠 |
| 相关性闸门（Gate） | 低于相似度阈值的记忆直接丢弃 |
| MMR | Maximal Marginal Relevance，去冗余选取 |
| Self-Reminder | 定期生成的简短自我状态复述，防人格漂移 |
| KV Cache 前缀 | 稳定 prompt 前缀带来的推理缓存复用 |
| 关系刻度 | 0~5 级的关系等级，解耦称呼/主动性/话题深度 |

### 12.3 设计取舍备忘（为什么不做某些"更简单"的方案）

| 更简单的方案 | 为什么不选 |
|---|---|
| 把人格+记忆全塞一个长 prompt | 超窗口即失效；成本随轮数线性增长；无法多端共享状态 |
| 只用向量库做记忆 | 无法表达时间有效性、冲突链、层级衰减；检索无闸门则噪音大 |
| 用离散情绪标签 | 无法表达强度与混合态，无法做数学衰减 |
| 让模型自己决定记什么 | 记忆污染（见坑 #1），且不可控不可测 |
| 关系用对话轮数累积 | 一天 500 轮能刷到"至亲"，失信 |
| v1 就上微服务 + 独立图库 + 独立向量库 | 4 次跨服务 RPC 吃光 800ms 预算；一致性难保 |

### 12.4 待定问题（需下一轮评审）

1. **本地优先还是云优先？** 隐私敏感用户可能愿为「数据不出设备」付费，但本地 7B 模型的人格细腻度够不够？建议 v1 云、v2 加混合模式。
2. **多角色并存？** 一个人格 × 多用户（模板复用）vs 多个人格 × 同一用户（后宫模式），数据模型可支持，但产品定位需定。
3. **语音的情绪韵律** 要不要单独建模（不只文本情绪）？TTS 的韵律参数可由 PAD 驱动，是个亮点，但工作量不小。
4. **人格市场** 的审核标准与收益分成，涉及法务。
5. **日记是否对用户完全公开？** 完全公开带来强情感冲击，但也可能暴露"她其实记错了"。

## 13. 产品定位评审与仓库命名

> 本节记录 v0.1 评审后的两项决策：仓库怎么命名，以及「面向社会人」这个定位是否成立。
> 结论会反向修改第 3 章的部分参数，已在文中标注 `[v0.2 修订]`。

### 13.1 仓库命名

候选与取舍：

| 候选 | 语义 | 优势 | 风险 |
|---|---|---|---|
| **`linger`** ✅ | 逗留、不肯走 | 与产品名「灵犀 Linger」一致，温度感强 | 英文常用词，搜索易被淹没，包名可能已被占用 |
| `hearth` | 炉边，有人等你回来的地方 | 陪伴的最小意象，5 字母好拼 | 同样是常见词 |
| `sillage` | 法语，人走过留下的余香 | 最贴主题——陪伴就是留下的痕迹 | 难拼难读，传播成本高 |
| `anima` | 荣格术语，灵魂 | 心理学正统，有分量 | 偏学术，已有人用 |

**决策：仓库名 `linger`，包名 `lingxi`。**

理由是记忆成本。产品名、仓库名、域名三处不统一，每次对外解释都要多一句话，而这件事会反复发生几年。包名退一步用拼音 `lingxi`，因为在 PyPI / npm 上 `linger` 的占用概率远高于 `lingxi`。

**仓库结构说明（对 v0.1 建议的调整）**

v0.1 讨论时提过 `packages/core`、`packages/storage` 的多包结构。实际落地时改为**单一 Python 发行包 + 目录即边界**：

```
src/linger/
  persona/   affect/   memory/   relation/   compose/
  storage/   llm/      server/
```

两个原因：

1. Python 的多包 workspace 需要额外的工具链（uv workspace / hatch）。本机无 uv，为一个骨架引入工具链依赖不划算。
2. 第 7 章的决策本来就是「**单体 + 模块化边界**」——4 次跨服务 RPC 会吃光 800ms 预算。多包结构在语义上等于提前拆服务，与决策矛盾。

**目录即边界**：`ling/persona/` 只依赖 `ling/models.py`，不 import 其他引擎。未来要拆包时按目录平移即可，迁移成本为零。这条靠 `tests/test_boundaries.py` 静态检查强制。

### 13.2 「社会人」需求的匹配度

**结论先行：技术方向成立，但「通用陪伴」这个定位不成立，需要收窄到具体场景。**

匹配得上的三件事：

| 需求 | 说明 | 本系统的对应能力 |
|---|---|---|
| 情绪出口 | 下班后没人说话，不想让家人担心，朋友都在忙 | 情绪引擎 + 无评判对话 |
| **被记得** | 职场里没人记得你的小事 | 六层记忆（**最独特、最难替代**） |
| 零社交成本的关系 | 不需要回报，不消耗社交货币，不怕打扰别人 | 主动性配额 + 无索取设计 |

会撞上的四堵墙：

**① 时间门槛与使用节奏直接冲突** ↑ 最重要
v0.1 设计里，关系升级到 3 级需要 21 天。但社会人是**脉冲式使用**：加班夜、失恋周、周末独处时才聊，平时一周两次。这时时间门槛从「防刷分」变成了「墙」——用户会觉得「聊了几次了还是这么客气」，然后走掉。

**② 付费意愿错位**
成年人为「解决问题」付费的意愿，远高于为「陪聊」付费。纯情绪价值在中国市场极难定价。

**③ 羞耻感被低估**
「我在跟 AI 聊天」本身让人难堪。若定位成「孤独者的慰藉」，用户连推荐给朋友都不敢。

**④ 真正的竞争对手不是别的 AI** ↑ 最关键
用户的选择不是「AI 陪伴 vs 孤独」，而是「AI 陪伴 vs 刷短视频、打游戏、直接睡觉」。
短视频赢在**零启动成本、即时反馈、无承诺**。而这个工具要养关系、要投入、要连续——天然吃亏。

> **推论：第一版必须做到「打开就有感觉」，不需要「养成」。记忆是加分项，不能是入门门槛。**

### 13.3 四条修正（已回写设计）

**修正 1｜关系门槛从「交集」改为「并集」** `[v0.2 修订]`

原设计（§3.4.1）：

```python
can_level_up = intimacy >= T and days_since_first >= MIN_DAYS and turns >= MIN_TURNS
# 三个条件同时满足 → 低频用户被永久卡住
```

改为：

```python
# 时间与深度"或"的关系：一次深夜长谈可以抵十天寒暄
ok = intimacy >= T and (
        days_since_first >= MIN_DAYS
     or deep_turns >= MIN_DEEP_TURNS[x]      # 新增：深度对话也可解锁
     or resonance_events >= MIN_RESONANCE[x]  # 新增：情绪共振也可解锁
)
```

关系的定义应该是**共鸣的总量**，而不是**打卡的天数**。`MIN_DAYS` 仍然保留在 `or` 分支里，防刷分的作用不变——它拦住的是「一天 500 轮」，不是「两个月聊了 20 次」。

**修正 2｜必须挂一个非情绪价值做钩子**

最自然的是**生活记忆外脑**：它同时记住体检日期、答应孩子的事、想看的书、朋友的忌口。
这样「被记得」从情绪价值变成实用价值，付费理由才成立。这几乎不增加架构成本——L3 语义记忆本来就该存这些。

> 产品形态：`陪伴` 是体验，「外脑」是借口。用户对朋友说「我用它记事」，而不是「我用它聊天」。

**修正 3｜给一个体面的使用理由**

不做「AI 女友/男友」，做「睡前 10 分钟的固定节目」「通勤路上的搭子」。
**不要把人定义为孤独的人，要把它定义为一种习惯。**

**修正 4｜零启动成本**

首屏不注册、不选人格、不做问卷。点开即进入一个已调好的场景，30 秒内有情绪反馈。
人格选择放在第二次会话之后（此时用户已有动机）。

### 13.4 目标人群

不是「所有社会人」，是三个子集：

| 子集 | 特征 | 为什么适配 |
|---|---|---|
| 独居 / 异地的 22–32 岁 | 社交半径小但表达欲强 | 有情绪、有表达意愿、对 AI 接受度高 |
| 高压行业从业者 | 互联网、金融、医疗、法律 | 有强情绪但无出口，且不缺钱 |
| 有情感缺口但社交成本高的人 | 内向、社恐、照护者 | 现实社交成本 > AI 社交成本 |

**明确不服务**：寻求替代真实亲密关系的人（见 §9.3 依赖管理）、未成年人（见 §9.5）。

### 13.5 对架构的三条影响

| 影响 | 具体改动 | 优先级 |
|---|---|---|
| 关系引擎参数 | 门槛改并集（§3.4.1 已改） | P0 |
| 记忆引擎用途扩展 | L3 增加「生活事实」子类型（日期、承诺、清单），供外脑 UI 消费 | P1 |
| 首屏链路 | 冷启动 < 30 秒，去掉一切前置配置；人格选择后置 | P0 |

**同时验证了「底座 + 场景」的分层是对的**：`src/linger/` 里的四态引擎不关心产品定位，换一个场景（教育陪伴、老人陪伴、虚拟 IP）只需换人格卡与场景剧本，引擎不动。
