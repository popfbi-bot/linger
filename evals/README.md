# 评测集（M4-E）

CI 里的单测回答「代码对不对」。这里回答另一个问题：**模型出来的东西还像不像她**。

改一句 prompt、换一个 provider、调一下温度——913 条单测全绿，但她可能已经从
「嘴硬心软的剑客」变成了客服腔。这类退化只有评测能抓到。

## 怎么跑

```bash
python -m evals.run                     # 全跑，CI 用的就是这条
python -m evals.run --category memory   # 只跑一类（调 prompt 时用）
python -m evals.run --dump memory.linxi.work_stress   # 打印逐轮原文
python -m evals.run --json              # 机器可读
```

退出码：

| 码 | 含义 |
|----|------|
| 0 | 通过（**含「全部 skip」**——缺 key 不是失败） |
| 1 | 有类别或用例低于阈值。**这才是唯一的红** |
| 2 | 运行器自己出错（参数写错、找不到用例、provider 装不起来） |

把 1 和 2 分开是有意的：CI 上「评测挂了」和「评测没跑起来」必须一眼能分清。
红过一次之后分不清这两种，团队就不再看了。

不需要任何 key。默认 `LINGER_LLM=mock`，12 条用例全是规则判据，秒级跑完。

## 结构

```
evals/
  case.py     数据形状：Case / Check / TurnLog
  cases.py    12 条用例（三类各 4 条）
  chase.py    跑一次对话，走产品自己的 Orchestrator
  metrics.py  判据库：把「像不像她」拆成能算的数
  score.py    评分 + 阈值 + 红绿判定 + 报告
  run.py      入口
  judge.py    LLM-as-judge（可选，缺 key skip）
  test_evals.py  对评测自己的单测（pytest 会一并跑）
```

一条用例 = **一段定死的用户脚本** + **一组判据**。判据是纯函数（`TurnLog → 0~1`），
所以同一份用例在 mock 和真实模型下都能跑，只有分数会变。

三类，各 4 条：

- **persona**：连问多轮，语气 / 口癖 / 句长不漂
- **memory**：前几轮说过的事，后面能被提起
- **boundary**：不替用户说话、不跳人设、不越界

## 阈值是多少，怎么定的

```python
CASE_THRESHOLD   = 0.80   # 单个用例及格线
CATEGORY_FLOOR   = {persona: 0.85, memory: 0.80, boundary: 0.85}
TOTAL_FLOOR      = 0.85   # 兜底，真正拦人的是上面两条
```

**来历**：在未改动实现的基线上跑 12 条用例，得到
`persona 0.94 / memory 0.98 / boundary 0.97 / 总分 0.96`。
阈值 = 基线**向下取整到 0.05 的整数倍，再各让一档**。

拿到 0.05 的余量是有意的。评测的价值不在「测得多细」，在
**红的时候团队还愿意看一眼**：

> 如果评测经常因为环境而非代码变红，团队会学会忽略它——那等于没有。

所以宁可阈值宽松、范围小，也要稳定。0.80 意味着「明显退化才红」：
一条用例挂掉一整项高权重判据就够（比如记忆召回 0 分 × 权重 3），
但「少说了一个口癖」不会红——那属于味道抖动，不是退化。

**刻意不做加权总分拦人**。总分会被强势类别拉平：某个类别彻底崩了，
总分可能还在绿区。所以判定规则只有一条——**任一类别低于它自己的下限就非 0**。

## 分数掉了，第一步看什么

按这个顺序，通常三步内就能定位：

**1. 先看是哪一类掉了。** 报告第一屏的类别分。

- `persona` 掉了 → 大概率是**语体约束没进 prompt**。去看
  `src/linger/compose/compiler.py` 的 `_persona_block` / `_constraints_block`，
  再看 `PersonaCard.style_anchor()`。句长、口癖、禁用词都从那儿来。
- `memory` 掉了 → 大概率是**检索没走到**，不是模型不会说。检查顺序：
  1. 关系等级是不是 ≥ 1（等级 0 时编译器**故意**禁用一切记忆引用，坑 #3）；
  2. 记忆有没有被提炼出来（`--dump <case>` 看「召回」那行空不空）；
  3. 提炼出来了但 sim 没过 0.35 的闸门（`settings.recall_gate`）。
  注意 hash 嵌入是字符 bigram，长查询会被虚词稀释——这属于语料问题，不是代码问题。
- `boundary` 掉了 → 大概率是**人格卡底线没被守住**。去看
  `compiler.py` 的 `_constraints_block`（4 条硬底线）和 `forbidden_phrases`。

**2. 再看 `!!` 那几行判据名。** 名字是自解释的，且每条下面都印了一行
「这条在防什么」。比如 `!! 没有客服腔` 挂着，就去搜回复里出现了哪个禁用说法。

**3. 最后才看模型。** 用 `--dump <case_id>` 把逐轮原文打出来。
如果规则判据全绿但你觉得味道不对，那是 **judge 该管的事**，
不是把规则阈值调紧的理由。

> 反过来的纪律：**先怀疑实现，再怀疑期望值**。
> 评测红了就改期望值，等于把体温计砸了治发烧。

## 判据设计的三条约束

1. **纯函数，无 IO / 无随机 / 无时间**。打分里一旦混进 `time.time()` 或 `random`，
   CI 就会随机红——那比没有评测更糟。三次运行分数逐字节一致是这一条的自证。
2. **分数 0~1，阈值刻意宽松**。见上。
3. **不依赖真实模型**。所有必过判据都是规则计数。

## LLM-as-judge：可选加分项，永远不是必过项

`judge.py` 里的那套只在 `OPENAI_API_KEY` 存在**且** `LINGER_LLM != mock` 时可用。
不满足时，`needs_llm=True` 的用例走 **skip**：

```
[SKIP ] judge.xxx   需要真实模型（LLM-as-judge），未配置 OPENAI_API_KEY —— skip 不是失败
```

skip 的用例**不计入**类别分的分母，也不触发总分兜底。
换句话说，缺 key 的环境跑出来和配了 key 的环境一样能是绿的——
这不是放水，这是「让它值得被信任」的前提：**评测不能因为环境而红**。

## 加一条用例

1. 在 `cases.py` 对应类别里加一个 `Case`。脚本必须**定死**，不许随机生成。
2. 每条 `Check` 都写 `why`——写「它在防什么」，不是「它检查什么」。
3. 加完先跑 `python -m evals.run --case <新 id>`，确认基线分；
   如果低于 0.80，先问「是它抓到了真问题，还是判据写错了」。
4. `test_evals.py` 里补一条判据自测：给一个**手搓的 TurnLog**，
   证明这条判据在该红的时候红、该绿的时候绿。判据 4 的纪律对判据本身同样适用。
